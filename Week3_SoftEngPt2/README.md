## How everything fits together

```
NL question
    │
    ▼
text2sql/decomposer.py           ── Task 2 (lookup or rule-based)
    │  (structured decomposition)
    ▼
text2sql/sql_generator.py        ── Task 3 (single template, 50/50 OK)
    │  (SQL string)
    ▼
text2sql/validator.py            ── Task 3/4 (SELECT-only, blocks DDL/DML)
    │
    ▼
text2sql/executor.py             ── Task 3/4 (run on Postgres, time it)
    │
    ├── on error → validator.attempt_autofix → retry
    │              (max 1 in run_benchmark.py, max 3 in /agent/sql)
    │
    ▼
text2sql/nl_answer.py            ── Task 4 (rule-based NL summary)
    │
    ▼
final response (sql, result, summary, status, retry_count, attempts[])
```

The same `Text2SQLPipeline` class is reused by:

- **`run_benchmark.py`** — Task 3 deliverable (50 questions, max_retries=1)
- **`POST /agent/sql`** — Task 4 deliverable (any question, max_retries=3)

## Step-by-step: run everything on your machine

> **Prerequisites:** Docker Desktop running, Python ≥ 3.10, `pip`. Tested on macOS, Linux, and Windows (WSL2).

### Step 0. Get the code

```bash
git clone https://github.com/rishavdevtiwari/fusemachines-for-prompting.git
cd fusemachines-for-prompting/Week3_SoftEngPt2/project
```

### Step 1. Create a virtual environment and install deps

```bash
# Linux / macOS
python3 -m venv .venv
source .venv/bin/activate

# Windows (PowerShell)
python -m venv .venv
.\.venv\Scripts\Activate.ps1

pip install -r requirements.txt
```

### Step 2. Set up the environment file

```bash
cp .env.example .env
# (No edits needed if you keep the docker-compose port 5433.)
```

`.env` content:

```env
DATABASE_URL=postgresql+psycopg2://postgres:postgres@localhost:5433/classicmodels
```

### Step 3. Start PostgreSQL and seed the database

```bash
docker compose up -d
# wait ~10s for the health-check to pass
docker compose ps
```

The first time you run this, Docker reads `seed.sql` from the project directory and creates the full ClassicModels schema (8 tables) plus the data (110 products, 122 customers, 326 orders, 2996 orderdetails, 273 payments, 23 employees, 7 offices, 7 productlines).

**Verify the seed:**

```bash
docker compose exec db psql -U postgres -d classicmodels \
  -c "SELECT 'customers' AS t, COUNT(*) FROM customers
      UNION ALL SELECT 'products',     COUNT(*) FROM products
      UNION ALL SELECT 'orders',       COUNT(*) FROM orders
      UNION ALL SELECT 'payments',     COUNT(*) FROM payments;"
```

Expected:

```
     t      | count
------------+-------
 customers  |   122
 products   |   110
 orders     |   326
 payments   |   273
```

### Step 4. Run the FastAPI server (for Task 4 + Week 2 endpoints)

```bash
# from project/
python main.py
# or, equivalently:
uvicorn main:app --host 0.0.0.0 --port 8000 --reload
```

Then in another terminal:

```bash
# Week 2 dashboard
curl http://127.0.0.1:8000/overall_counts | python -m json.tool

# Task 4 agent
curl -X POST http://127.0.0.1:8000/agent/sql \
     -H 'Content-Type: application/json' \
     -d '{"question": "How many shipped orders are from USA customers?"}' \
     | python -m json.tool
```

Interactive Swagger UI at <http://127.0.0.1:8000/docs>.

### Step 5. Run the Task 3 benchmark

In a separate terminal (with the venv active and the DB running):

```bash
python run_benchmark.py
```

You should see 50 lines like `[PASS] Q 1 (A) List all products …` and at the end:

```

Wrote text2sql/logs/benchmark_results.csv
Wrote ../deliverables/Task3_Benchmark_Report.md
```

Open `deliverables/Task3_Benchmark_Report.md` to see the aggregate scorecard.

### Step 6. Run the smoke tests

```bash

# Hits the live /agent/sql endpoint with 4 cases and asserts each.
# (Server must be running.)
python test_agent.py
```

## Per-task walkthrough

### Task 1 Part 1 — Ground-truth SQL

I wrote `Task1_GroundTruth_SQL.md` with all 50 questions answered, organised into 4 sections so you can grade them in batches:

- **A** — single-table SELECT / DISTINCT (Q1–Q20)
- **B** — joins / left-joins / self-join (Q21–Q30)
- **C** — `GROUP BY` aggregates (Q31–Q40)
- **D** — whole-table aggregates (Q41–Q50)

For each query I include the SQL, an explanation, and a verification hint (count + a few sample rows). To capture the screenshots required by the assignment, run each query in psql/DBeaver and screenshot the result grid. The doc also gives you a `\copy` command if you'd rather export to CSV.

### Task 1 Part 2 — Evaluation framework

`Task1_Evaluation_Framework.md` defines an 8-axis evaluation framework with a composite score:

```
Composite = 0.35·C2 + 0.20·C3a + 0.15·C3b + 0.20·R2 + 0.10·C1
```

The headline insight in the document: **never** evaluate Text-to-SQL by string-matching the SQL output. Equivalent queries can be very different strings. The right yardstick is **result-set equality** (multiset of value tuples, with float tolerance), captured precisely in §3 of the doc. The framework also includes a 10-bucket failure-mode taxonomy so the report tells you *what to fix*, not just a number.

### Task 2 — Structured decomposition

For each of the 50 questions, `Task2_Decomposition.md` records:

- **Intent** (one-line description of what's being asked)
- **Tables** involved (with aliases for joins)
- **Columns** to project / aggregate
- **Filters** (`WHERE` — none in this benchmark, but the schema supports them)
- **Joins** (type + table + on-condition)
- **Group By** (for aggregates)
- **Order By** and **Distinct** as derived flags

The same data is stored machine-readable in `Task2_Decomposition.json`, which the Task 3 pipeline consumes directly. So the decomposition isn't just documentation — it's the input wire format for the SQL generator.

### Task 3 — Pipeline + benchmark

The pipeline is a **rule-based** Option-1 implementation (Task 3 explicitly allows this; Option 2 would swap `decomposer.py` for an LLM prompt chain — the rest of the pipeline is unchanged). Six modules:

| Module | Job | Lines |
|--------|-----|------:|
| `decomposer.py` | NL → decomposition (lookup + keyword fallback) | ~150 |
| `sql_generator.py` | decomposition → SQL via one template | ~40 |
| `validator.py` | SELECT-only safety check + auto-fix | ~100 |
| `executor.py` | run on Postgres, return rows / error / time | ~60 |
| `nl_answer.py` | result rows → human-readable summary | ~50 |
| `pipeline.py` | orchestrator with retry loop and audit log | ~150 |

The benchmark runner (`run_benchmark.py`) compares each generated query against the ground-truth result set using the algorithm from the evaluation framework, then writes a CSV + Markdown report.

**Latest run summary** (regenerate any time with `python run_benchmark.py`):

| Axis | Score |
|------|------:|
| Execution success rate (C1) | 100% |
| Result-set equality (C2) | 100% |
| Schema-link table accuracy (C3a) | 100% |
| Schema-link column accuracy (C3b) | 100% |
| Final-answer success rate (R2) | 100% |
| p50 latency | ~0.6 ms |
| p95 latency | ~1.6 ms |
| **Composite score** | **100%** |

### Task 4 — Mini SQL Agent endpoint

The endpoint reuses the same pipeline with `max_retries=3`:

```bash
POST /agent/sql
Content-Type: application/json

{ "question": "How many shipped orders are from USA customers?" }
```

Response shape (Pydantic-validated):

```json
{
  "sql":  "SELECT ...",
  "result": 42,
  "summary": "There are 42 shipped orders from customers in USA.",
  "status": "success",
  "error":  null,
  "decomposition": { ... },
  "retry_count": 0,
  "attempts": [
    {"attempt": 1, "sql": "...", "ok": true, "elapsed_ms": 4.1, "row_count": 1, "error": null}
  ],
  "elapsed_ms": 4.12
}
```

Safety properties (asserted by `test_agent.py`):

1. **Read-only** — the agent **never** generates `INSERT/UPDATE/DELETE/DROP/ALTER/TRUNCATE/CREATE/GRANT/REVOKE/MERGE/COPY/VACUUM/REINDEX/CLUSTER/REFRESH`. The validator hard-rejects any such SQL before execution. Even when the question text contains `DROP TABLE customers; --`, the agent emits a benign `SELECT * FROM customers`.
2. **Bounded retries** — at most 3 retries per request (Task 4 spec).
3. **Single statement** — the validator rejects multi-statement payloads.
4. **Structured logging** — every attempt is written to `text2sql/logs/pipeline.log` and surfaced to the client in the `attempts` array.

## Where to look when something breaks

| Symptom | Where to look |
|---------|---------------|
| `connection refused on port 5433` | `docker compose ps` — is the DB up? `docker compose logs db` |
| `relation "customers" does not exist` | seed didn't run. `docker compose down -v && docker compose up -d` |
| `NoneType` errors at startup | check `.env` exists and `DATABASE_URL` is set |
| `/agent/sql` returns wrong SQL | `text2sql/logs/pipeline.log` shows decomposition + every attempt |
| Benchmark report shows `0%` C1 | DB unreachable. Check `DATABASE_URL` and `docker compose ps` |
